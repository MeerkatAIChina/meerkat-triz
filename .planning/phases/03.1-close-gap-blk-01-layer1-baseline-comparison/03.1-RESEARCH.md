## Summary

This phase closes audit gap BLK-01 by making Notebook 05 load actual Layer 1 (lm-eval-harness) benchmark scores from the baseline JSON file produced in Notebook 03, and by re-running the same Layer 1 suite on the fine-tuned adapter so the before/after comparison report computes meaningful deltas. The required changes are small and localized: (1) Notebook 03 must register the path to the raw lm-eval JSON in `pipeline_state` artifact metadata, (2) Notebook 05 must read that JSON instead of using `baseline['metadata']`, (3) Notebook 05 must run `run_lm_evaluation()` on the adapter, and (4) `aggregate_results()` must accept `layer1_general` inside `before_results`/`after_results` and compute per-task deltas using the existing `_compute_deltas()` helper. No new external packages are required.

**Primary recommendation:** Extend `aggregate_results()` to detect `layer1_general` keys in `before_results`/`after_results`, store deltas under `report["layer1_general"]`, and update the two notebooks so the baseline artifact carries `metadata.layer1_path` and Notebook 05 loads the JSON at that path and re-runs the suite on the adapter.

- **Baseline artifact schema (D-01):** Notebook 03 keeps `baseline_results.path` pointing at the aggregate benchmark report / `results/` directory. - **Adapter Layer 1 source (D-02):** Notebook 05 re-runs the full Layer 1 suite (MMLU-Pro, GPQA, HumanEval, MATH, BBH as configured in `BENCHMARK_CONFIG`) on the adapter after Layer 2 TRIZ and Layer 3 performance benchmarks. In comparison mode, `aggregate_results()` reads `layer1_general` from each dict, computes per-task deltas using `_compute_deltas()`, and stores the result under `report["layer1_general"]`. ### Pattern 1: Baseline Artifact Registration in Notebook 03
**What:** After `run_lm_evaluation()` returns, register the raw JSON path and a compact summary in `pipeline_state`.
**When to use:** Always — this is the only way Notebook 05 can locate the full Layer 1 scores.
**Example:**
```python
# Source: derived from 03.1-CONTEXT.md D-01 and existing Notebook 03 cell 10 [VERIFIED]

from pathlib import Path

# run_lm_evaluation already saved the file and returned the dict

# Find the file it just wrote

latest_layer1_file = max(result_files, key=lambda p: p.stat().st_mtime)

# Build a compact summary: one primary metric per configured task
layer1_summary = {}
for task in tasks:
    task_results = general_results.get('results', {}).get(task, {})
    # Primary metric heuristic (Claude's Discretion)
    for candidate in ['acc_norm', 'acc', 'exact_match', 'pass_at_1']:
        if candidate in task_results:
            layer1_summary[task] = {candidate: task_results[candidate]}
            break

state = PipelineState()
state.register(
    name='baseline_results',
    path=str(latest_aggregate_report) if latest_aggregate_report else str(RESULTS_DIR),
    artifact_type='benchmark',
    metadata={
        'model_path': model_path,
        'model_dtype': '4-bit_nf4',
        'tasks': tasks,
        'layer1_path': str(latest_layer1_file),
        'layer1_summary': layer1_summary,
        'perf_throughput': perf_results.get('throughput_tokens_per_sec', 'N/A'),
        'timestamp': datetime.now().isoformat(),

)
```

### Pattern 5: Extracting a Flat Metric Dict from lm-eval JSON
**What:** Convert lm-eval's nested `results.{task}.{metric}` structure into a flat `{task: value}` dict suitable for `_compute_deltas()`.
**When to use:** Inside `aggregate_results()` when processing `layer1_general`.
**Example:**
```python
# Source: derived from print_evaluation_summary() and 03.1-CONTEXT.md Claude's Discretion [VERIFIED]
def _extract_layer1_metrics(lm_eval_results: dict) -> dict:
    """Return {task: primary_value} from an lm-eval results dict."""
    metrics = {}
    for task, task_results in lm_eval_results.get('results', {}).items():
        # Pick primary metric in order of preference
        for candidate in ['acc_norm', 'acc', 'exact_match', 'pass_at_1']:
            if candidate in task_results:
                metrics[task] = task_results[candidate]
                break
        else:
            # Fallback: first scalar metric containing 'acc' or 'score'
            for key, value in task_results.items():
                if isinstance(value, (int, float)) and ('acc' in key or 'score' in key):
                    metrics[task] = value
                    break
    return metrics
```

### Anti-Patterns to Avoid
- **Storing only summary metadata and throwing away the raw JSON:** Notebook 05 currently does `general_results = baseline.get('metadata', {})`, which lacks per-task metric values. The raw JSON must be preserved and referenced. [VERIFIED: 03.1-CONTEXT.md specifics]
- **Re-running Layer 1 on the base model during Notebook 05:** D-02 explicitly says adapter Layer 1 scores come from a re-run on the adapter; the base (before) scores come from the baseline artifact. Re-running the full base Layer 1 suite would duplicate hours of work. [VERIFIED: 03.1-CONTEXT.md D-02]
- **Changing the existing `general_results` parameter signature:** Removing or renaming `general_results` would break backward compatibility and existing tests. Keep it additive. [VERIFIED: 03.1-CONTEXT.md D-03]
- **Deep-nesting the Layer 1 delta table:** `_compute_deltas()` produces `{metric: {before, after, delta, delta_pct}}`. Keep Layer 1 at the same level as Layer 2/Layer 3 so `display_delta_table()` works without special cases. [VERIFIED: existing Notebook 05 cell 23]

## Common Pitfalls

### Pitfall 1: Notebook 05 Loads Metadata Instead of the Raw JSON
**What goes wrong:** `general_results = baseline.get('metadata', {})` only contains the small summary (`tasks`, `perf_throughput`, maybe `triz_summary`). The delta table for Layer 1 ends up empty or nonsensical.
**Why it happens:** The current Notebook 05 cell 19 was written before BLK-01 was identified; it never expected a separate JSON file.
**How to avoid:** Read `baseline['metadata']['layer1_path']` and `json.load()` that file. Keep the summary for quick human display only. [VERIFIED: 03.1-CONTEXT.md D-01]
**Warning signs:** `report['layer1_general']['metrics']` contains only string keys like `"tasks"` and `"perf_throughput"` instead of task scores.

### Pitfall 2: `aggregate_results()` Overwrites Existing Test Outputs
**What goes wrong:** Adding `layer1_general` delta computation changes the shape of `report["layer1_general"]` and breaks `tests/test_benchmark_utils.py` assertions that assume a specific summary.
**Why it happens:** The existing tests only check `report["summary"]` keys and values; any change to Layer 1 handling must not alter `summary` when `layer1_general` is absent.
**How to avoid:** Only enter the new delta branch when `before_results`/`after_results` contain `layer1_general`. Leave the existing `general_results` single-run path untouched. [VERIFIED: 03.1-CONTEXT.md D-03]
**Warning signs:** `pytest tests/test_benchmark_utils.py -x` fails on `TestAggregateResults`.

### Pitfall 3: Adapter Layer 1 Run Uses the Wrong Model or Tokenizer
**What goes wrong:** `run_lm_evaluation()` is called with `model=None` and re-loads the base model from disk, or the adapter is passed but the tokenizer is stale.
**Why it happens:** The function has an optional `model`/`tokenizer` pair; omitting them falls back to the `model_args` string path.
**How to avoid:** Pass `model=model` and `tokenizer=tokenizer` explicitly in Notebook 05 after adapter loading, mirroring Notebook 03. [VERIFIED: `benchmark_utils.py::run_lm_evaluation()` signature]
**Warning signs:** Layer 1 "after" scores equal baseline scores exactly, or the run fails with a quantization/dtype mismatch.

### Pitfall 4: Missing `layer1_path` Goes Unnoticed
**What goes wrong:** Notebook 05 silently sets `general_results = None` and produces a report with no Layer 1 data, defeating the purpose of BLK-01.
**Why it happens:** If `baseline` exists but `metadata.layer1_path` is absent, the code may skip the fallback because "a baseline was found."
**How to avoid:** Treat missing `layer1_path` the same as missing baseline artifact: trigger the quick baseline fallback and print the warning. [VERIFIED: 03.1-CONTEXT.md D-04]
**Warning signs:** Report shows `layer1_general.source = "pipeline_state"` with empty metrics.

### Pitfall 5: Heuristic Primary Metric Selection Picks the Wrong Key
**What goes wrong:** For a task like MMLU-Pro, `acc_norm` may differ from `acc`; picking the wrong one makes deltas inconsistent with published numbers.
**Why it happens:** lm-eval tasks expose multiple metrics; the "primary" metric is task-dependent and not always labeled.
**How to avoid:** Document the heuristic explicitly and prefer the canonical primary metric where known (`acc_norm` > `acc` > `exact_match` > `pass_at_1`). Allow the full task results to remain available in the saved JSON for audit. [Claude's Discretion]
**Warning signs:** Layer 1 delta percentages look implausible (e.g., ±0% when human inspection of the JSON shows movement).

### Pitfall 6: OOM When Running Full Layer 1 on FP16 Adapter After Other Benchmarks
**What goes wrong:** Notebook 05 has already loaded the adapter (FP16), run Layer 2 and Layer 3, then loaded the base model (FP16) for before comparison. Running Layer 1 on the adapter after the base model load means both model objects may still be referenced.
**Why it happens:** Python may not release the base model before the adapter Layer 1 run if references are not deleted.
**How to avoid:** After base-model Layer 2/Layer 3, `del model; torch.cuda.empty_cache(); gc.collect()` before reloading the adapter (or restructure the notebook so adapter Layer 1 runs while the adapter model is still the active model). [ASSUMED]
**Warning signs:** `torch.cuda.OutOfMemoryError` during the adapter Layer 1 cell.

## Open Questions

1. **Should adapter Layer 1 results be cached to disk?**
   - What we know: The full Layer 1 suite may take hours. Re-running Notebook 05 would duplicate work.
   - What's unclear: Whether the user wants to pay the storage/complexity cost for a cache file.
   - Recommendation: Start without caching (simplest). If runtime becomes painful, add a `results/lm_eval_results_adapter_*.json` lookup in a follow-up.

2. **What should the quick baseline fallback task be?**
   - What we know: `BENCHMARK_CONFIG['general_benchmarks']` lists `mmlu_pro`, `gpqa`, `humaneval`, `math`, `bbh`.
   - What's unclear: Which is fastest and most representative on the base model.
   - Recommendation: Use `mmlu_pro` with its configured 5-shot setting; it is general, well-known, and a reasonable proxy. Document as "quick baseline only."

3. **How should individual task failures inside the adapter Layer 1 run be handled?**
   - What we know: `run_lm_evaluation()` already logs warnings and continues for failed tasks.
   - What's unclear: Whether Notebook 05 should fail the cell or record `null` deltas.
   - Recommendation: Match existing `run_lm_evaluation()` behavior: log warning, skip failed task, and let `_compute_deltas()` produce `null`/`0` for missing keys. Do not fail the whole report.

# Phase 03.1: Code Review Report

**Reviewed:** 2026-06-30T12:45:00Z
**Depth:** standard
**Files Reviewed:** 6
**Status:** issues_found

## Summary

Phase 03.1 adds Layer 1 baseline comparison support: notebook 03 persists the raw lm-eval JSON path and a compact summary in `pipeline_state`; notebook 05 re-runs Layer 1 on the fine-tuned adapter and loads the baseline file with path-traversal protection; `benchmark_utils.py` gains `_extract_layer1_metrics` and before/after delta logic for Layer 1. The core design is sound, but two runtime defects were introduced in notebook 05 by forgetting to import `BENCHMARK_CONFIG`, and several robustness/methodology issues remain in the new cells and tests.

## Critical Issues

### CR-01: Notebook 05 cell-10 references `BENCHMARK_CONFIG` without importing it

**File:** `ref/mongoose_ai_dgx/notebooks/05_model_evaluation.ipynb` cell-10
**Issue:** The new adapter Layer 1 evaluation cell executes `tasks = list(BENCHMARK_CONFIG['general_benchmarks'].keys())`, but the cell only imports `MODELS_DIR, RESULTS_DIR, BASE_MODEL, DATA_DIR` from `config`. This raises `NameError: name 'BENCHMARK_CONFIG' is not defined` and stops the cell before any Layer 1 after-fine-tuning results are produced.
**Fix:** Add `BENCHMARK_CONFIG` to the cell's `config` import.

```python
from config import MODELS_DIR, RESULTS_DIR, BASE_MODEL, DATA_DIR, BENCHMARK_CONFIG
```

### CR-02: Notebook 05 cell-21 references `BENCHMARK_CONFIG` without importing it

**File:** `ref/mongoose_ai_dgx/notebooks/05_model_evaluation.ipynb` cell-21
**Issue:** The baseline-loading fallback branch executes `quick_config = BENCHMARK_CONFIG['general_benchmarks'][quick_task]`, but `BENCHMARK_CONFIG` is not imported in this cell either. Whenever the stored baseline path is missing or invalid, the notebook falls back to a quick baseline and immediately crashes with `NameError`.
**Fix:** Add `BENCHMARK_CONFIG` to the cell's `config` import (same as CR-01).

## Warnings

### WR-01: Layer 1 adapter evaluation hardcodes `num_fewshot=5`

**File:** `ref/mongoose_ai_dgx/notebooks/05_model_evaluation.ipynb` cell-10
**Issue:** The new Layer 1 run passes `num_fewshot=5` for every task. `config.py` defines per-task few-shot counts (`mmlu_pro: 5`, `gpqa: 0`, `humaneval: 0`, `math: 4`, `bbh: 3`). Notebook 03 reads those per-task values, so the adapter scores will not be comparable to the baseline scores even after the import fix.
**Fix:** Use the per-task configuration. If `lm-eval` / `run_lm_evaluation` requires a single scalar, invoke it once per task with that task's configured `num_fewshot` and aggregate the outputs, or extend `run_lm_evaluation` to accept a per-task few-shot mapping.

### WR-02: Quick baseline fallback reloads the base model instead of reusing the loaded instance

**File:** `ref/mongoose_ai_dgx/notebooks/05_model_evaluation.ipynb` cell-21
**Issue:** When no baseline file is available, the fallback calls `run_lm_evaluation(model_path=base_model_path, ...)` without passing the already-loaded `model` and `tokenizer` from cell 15. This forces `lm-eval` to load the 35B base model a second time in FP16, risking out-of-memory on the 128GB DGX Spark.
**Fix:** Pass the loaded instances to avoid the duplicate load:

```python
baseline_layer1 = run_lm_evaluation(
    model_path=base_model_path,
    tasks=[quick_task],
    output_dir=RESULTS_DIR,
    num_fewshot=quick_config['num_fewshot'],
    batch_size=1,
    model=model,
    tokenizer=tokenizer,
)
```

### WR-03: Notebook 05 cell-23 passes undefined `general_results` to `aggregate_results`

**File:** `ref/mongoose_ai_dgx/notebooks/05_model_evaluation.ipynb` cell-23
**Issue:** The `aggregate_results` call passes `general_results=general_results if 'general_results' in dir() else None`. `general_results` is no longer assigned anywhere in notebook 05 (the pre-phase version loaded it from baseline metadata). The `in dir()` guard prevents a crash, but the parameter is dead code, obscures intent, and could mislead future maintainers into thinking Layer 1 can come from that argument.
**Fix:** Remove the `general_results` keyword or pass `None` explicitly, since Layer 1 is now supplied through `before_results` / `after_results`.

### WR-04: `_extract_layer1_metrics` rejects numpy scalar metric values

**File:** `ref/mongoose_ai_dgx/utils/benchmark_utils.py:132-162`
**Issue:** The function checks `isinstance(value, (int, float))`. `lm-eval-harness` can return `numpy.float64` values before JSON serialization, and those fail the isinstance check, causing metrics to be silently skipped when `_extract_layer1_metrics` is called on raw evaluation output.
**Fix:** Accept numpy scalars and normalize them, for example:

```python
import numpy as np

for key in preference:
    val = task_results.get(key)
    if isinstance(val, (int, float, np.floating, np.integer)):
        value = float(val)
        break
```

### WR-05: Test asserts source-code presence rather than behavior

**File:** `ref/mongoose_ai_dgx/tests/test_benchmark_utils.py:378-384`
**Issue:** `test_evaluate_case_quality_calls_bleu_rouge` uses `inspect.getsource(benchmark_utils.TRIZBenchmark.evaluate_case_quality)` and asserts that the strings `_compute_bleu` and `_compute_rouge` appear in the method body. This tests implementation detail, not behavior, and will break if the helpers are renamed, inlined, or moved.
**Fix:** Refactor the test to assert that `evaluate_case_quality` returns non-empty `bleu` and `rouge` results when references are provided, or mock `_compute_bleu` / `_compute_rouge` and assert they are called.

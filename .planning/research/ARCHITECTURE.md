## Current Architecture Overview

The project follows a **notebook-driven execution model** on an NVIDIA DGX Spark (128GB Unified Memory). The codebase is structured as a Python package (`utils/`) with thin Jupyter notebook orchestration layers. The architecture has three conceptual tiers:

```
┌─────────────────────────────────────────────────────────────┐
│  NOTEBOOK ORCHESTRATION (01–05 + 02b)                       │
│  Cell-by-cell execution, manual checkpointing, human review  │
├─────────────────────────────────────────────────────────────┤
│  PYTHON UTILS PACKAGE (config, data_utils, training_utils,  │
│  benchmark_utils) — pure functions, no side effects          │
├─────────────────────────────────────────────────────────────┤
│  EXTERNAL DEPENDENCIES (transformers, PEFT, TRL,            │
│  lm-eval-harness, datasets)                                  │
└─────────────────────────────────────────────────────────────┘
```

### Existing Component Inventory

| Component | File | Responsibility | Notebook Consumers |
|-----------|------|---------------|-------------------|
| `config.py` | Centralized constants | Paths, hyperparameters, hardware config | All notebooks |
| `data_utils.py` | Data loading, ChatML conversion, synthetic generation, validation, splitting | 02_data_preparation.ipynb |
| `training_utils.py` | Model loading (4-bit), QLoRA config, training args, SFTTrainer creation, save/merge | 01, 04 |
| `benchmark_utils.py` | Three-layer evaluation (lm-eval, TRIZ custom, performance), result aggregation | 03, 05 |
| `notebooks/01–05` | Orchestration cells | End-to-end workflow |

## Integration Analysis: What the Execution Phase Needs

The current milestone (v1.0 First Training Run) requires executing the full pipeline end-to-end. The question is: **what architectural changes are needed to bridge the gap between the current notebook skeleton and a runnable training pipeline?**

### Finding 1: The Notebooks Are Thin Orchestrators — Most Logic Is Already in Utils

The notebooks contain almost no business logic. They are import-and-call wrappers around the `utils/` functions. This means the "integration" work is primarily about:

1. **Ensuring notebook cells are executable** (imports resolve, paths exist, data is present).
2. **Handling state persistence between notebooks** (model paths, adapter paths, result files).
3. **Orchestrating the 02b synthetic generation step**, which is mentioned in `PROJECT.md` ("6-stage, Moonshot API") but **has no notebook or utility code** in the current codebase.

### Finding 2: Critical Gap — Notebook 02b (Synthetic Data Generation) Is Missing

`PROJECT.md` lists "Synthetic data generation pipeline (6-stage, Moonshot API)" as validated, but:

- No `02b_synthetic_generation.ipynb` exists in `notebooks/`.
- `data_utils.py` contains `create_synthetic_data()` and `vary_sample()`, but these implement **naive template-based paraphrasing** (prefix insertion, answer extension), not the Moonshot API pipeline.
- The audit report (referenced in `CLAUDE.md`) flagged this: "Synthetic data generation uses simple paraphrase templates. For production-quality training, a GPT-4o-based synthesis pipeline with expert review is recommended."

**Implication:** The ~6K synthetic training samples required for the milestone **cannot be generated by existing code**. This is the single largest architectural gap.

### Finding 3: State Management Is Implicit and Fragile

The notebooks rely on:
- Hardcoded paths in `config.py` (`/home/meerkat/mongoose_ai`).
- Manual cell execution order.
- Manual cleanup (`del model; torch.cuda.empty_cache()`) between phases.
- No formal artifact registry or pipeline state tracking.

**Risk:** If notebook 03 crashes after running for 4 hours, there is no resume mechanism except TRL's checkpointing (which only covers training, not evaluation). The baseline results are not automatically fed into the post-training comparison in notebook 05.

### Finding 4: Data Flow Between Notebooks Is File-Based and Unvalidated

| Handoff | Producer | Consumer | Artifact | Validation |
|---------|----------|----------|----------|------------|
| Raw → Processed | 02 | 04 | `processed/{train,val,test}.jsonl` | `validate_chatml_format()` |
| Base model | 01 | 03, 04 | `models/Qwen3.6-35B-A3B/` | Smoke test in 01 |
| Adapter | 04 | 05 | `models/meerkat_triz_adapter_v1/` | None (assumed exists) |
| Baseline results | 03 | 05 | `results/*_benchmark_*.json` | None (manual comparison) |

The 03→05 comparison is **manual** (notebook 05 hardcodes `before_score = 0.35`). There is no automatic loading of baseline results.

### Finding 5: The `create_trainer()` Function Has a Critical Design Decision That Must Be Preserved

From `training_utils.py` (lines 333–436):

- Uses `SFTTrainer` with `formatting_func` parameter.
- **Does NOT pass `data_collator`** — this was a fix for CR-001 (SFTTrainer + DataCollatorForLanguageModeling conflict).
- Uses `tokenizer.apply_chat_template()` inside `formatting_func` to ensure training format matches inference format.

**Any new execution wrapper must preserve this exact pattern.** Passing a `data_collator` to `SFTTrainer` would reintroduce the bug.

### Finding 6: Target Modules Must Be Explicit — "all-linear" Is Dangerous

From `training_utils.py` (lines 127–145) and `CLAUDE.md`:

- Qwen3.6 has a hybrid architecture: 10 Gated Attention layers + 30 Gated DeltaNet layers + MoE MLP.
- The explicit module list covers: `q_proj`, `k_proj`, `v_proj`, `o_proj`, `in_proj_qkv`, `in_proj_z`, `in_proj_b`, `in_proj_a`, `out_proj`, `gate_proj`, `up_proj`, `down_proj`.
- `README.md` incorrectly says "默认使用 'all-linear' 自动检测" — this contradicts the audit fix (CR-002) and the actual `config.py` which uses the explicit list.

**Implication:** The execution pipeline must use the explicit list from `config.py`. The README should be updated to match.

## Recommended Architecture for Execution Integration

### Option A: Minimal Change — Fix Gaps, Keep Notebook-Driven (Recommended)

Keep the notebook-driven model but add the missing pieces:

1. **Create `02b_synthetic_generation.ipynb`** — Moonshot API integration notebook.
2. **Add `synthetic_pipeline.py` to `utils/`** — Encapsulate the Moonshot API calls, rate limiting, batching, and output validation.
3. **Add `pipeline_state.py` to `utils/`** — Simple JSON-based artifact registry tracking:
   - Which notebooks have run successfully
   - Paths to generated artifacts
   - Baseline results for automatic comparison
4. **Update `05_model_evaluation.ipynb`** — Auto-load baseline results from `pipeline_state` instead of hardcoding.

**Pros:** Least disruption, matches current team workflow, preserves human review points.
**Cons:** Still requires manual notebook execution, no CI/CD integration.

### Option B: Script Wrapper — Notebooks + CLI Entry Points

Add CLI scripts that wrap the utils functions for headless execution:

```
scripts/
  run_02b_generate.py      # Synthetic data generation
  run_03_benchmark.py      # Baseline evaluation
  run_04_train.py          # QLoRA training
  run_05_evaluate.py       # Post-training evaluation
  run_pipeline.py          # Orchestrates 02b→03→04→05 with state tracking
```

Each script:
- Loads config from `config.py`
- Calls utils functions
- Writes state to `pipeline_state.json`
- Supports `--resume-from` for checkpoint recovery

**Pros:** Enables automated/scheduled runs, better for reproducibility.
**Cons:** More code to maintain, notebooks and scripts can drift.

### Option C: Full Pipeline Framework (Overkill)

Introduce a framework like Prefect, Airflow, or MLflow Pipelines.

**Verdict:** NOT recommended. The project has 5 steps, runs on a single machine, and the team is already comfortable with notebooks. Framework overhead exceeds value.

## Data Flow Changes for Execution Phase

### Current Flow (with gaps)

```
01_setup → 02_data_prep → [GAP: 02b missing] → 03_baseline → 04_train → 05_eval
```

### Target Flow (after integration)

```
01_setup
   ↓
02_data_prep (loads 548 seed samples)
   ↓
02b_synthetic_gen (Moonshot API → ~6K samples)
   ↓
02_data_prep (re-run: converts 6K samples to ChatML, split, save)
   ↓
03_baseline (load base model → run 3-layer eval → save results to state)
   ↓
04_train (load processed data + base model → QLoRA → save adapter + checkpoints)
   ↓
05_eval (load adapter → run 3-layer eval → auto-compare with baseline from state)
```

### Key Data Flow Rules

1. **Notebook 02 and 02b are coupled:** After synthetic generation, notebook 02 must be re-executed to regenerate the ChatML-format dataset from the expanded raw data.
2. **Notebook 03 and 05 share state:** The baseline results from 03 must be automatically discoverable by 05. A `pipeline_state.json` in `OUTPUTS_DIR/` is the simplest mechanism.
3. **Adapter path is a contract:** Notebook 04 saves to `models/meerkat_triz_adapter_v1/`. Notebook 05 loads from the same path via `AutoPeftModelForCausalLM.from_pretrained()`. This convention must be preserved.
4. **Checkpoint recovery:** Notebook 04 supports `trainer.train(resume_from_checkpoint=...)` via `resume_from_checkpoint()` in `training_utils.py`. The execution pipeline should expose this.

## Anti-Patterns to Avoid

### Anti-Pattern 1: Reintroducing `data_collator` into `create_trainer()`
**What:** Passing a custom `DataCollatorForLanguageModeling` to `SFTTrainer`.
**Why bad:** Conflicts with SFTTrainer's internal label-masking logic. Causes incorrect loss computation (CR-001).
**Instead:** Keep `formatting_func` pattern, no `data_collator`.

### Anti-Pattern 2: Using `"all-linear"` for `target_modules`
**What:** Letting PEFT auto-detect linear layers on Qwen3.6.
**Why bad:** Hybrid architecture (Gated DeltaNet + Gated Attention + MoE) may incorrectly include `lm_head` or miss specialized projection layers.
**Instead:** Use explicit module list from `config.py` / `get_qwen36_target_modules()`.

### Anti-Pattern 3: Hardcoding ChatML Format Strings
**What:** Manually constructing `<|im_start|>...<|im_end|>` strings.
**Why bad:** Format may diverge from model's actual chat template, causing training/inference mismatch.
**Instead:** Always use `tokenizer.apply_chat_template()`.

### Anti-Pattern 4: Running 04 Without 03 Baseline
**What:** Skipping baseline evaluation to save time.
**Why bad:** No way to measure whether fine-tuning improved or degraded capabilities.
**Instead:** Enforce 03→04→05 sequence via pipeline state checks.
